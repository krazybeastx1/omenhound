## Install

Requires Go 1.26+ (newer Go releases fetch the toolchain automatically):

```bash
go install github.com/krazybeastx1/omenhound/cmd/omenhound@latest
```

The binary is written to `$(go env GOPATH)/bin` (usually `~/go/bin`). If that is
not on your `PATH`:

```bash
export PATH="$PATH:$(go env GOPATH)/bin"
omenhound version
```

Pin an exact release with `@v0.1.0` (any published tag works). Each
[release](https://github.com/krazybeastx1/omenhound/releases) also ships prebuilt
linux/macOS/Windows tarballs — with `checksums.txt` — for hosts without a Go
toolchain.

Or build from source:

```bash
git clone git@github.com:krazybeastx1/omenhound.git
cd omenhound
make build                     # -> bin/omenhound
```

## What it is

OmenHound is a Go implementation of the BloodHound CE model:

| Piece | What it does |
|---|---|
| **Collector** (`omenhound collect`) | Enumerates AD over **LDAPS** (users, groups, computers, membership; `-c acl` object security descriptors → ACL edges; `-c container` OUs/GPOs/containers → `Contains`/`GPLink`; `-c trusts` → `TrustedBy`) and over **SMB/RPC** (`-c session`/`localadmin`/`rdp`/`dcom`/`psremote`/`loggedon` → `HasSession`/`AdminTo`/`CanRDP`/`ExecuteDCOM`/`CanPSRemote`), emitting a graph. Simple bind, NTLM and pass-the-hash (LDAPS recommended); BloodHound.py-compatible flags; `--zip` writes a real **BloodHound CE v5 archive**. |
| **Importer** (`omenhound import`) | Reads **BloodHound CE JSON** and **`bloodhound-ce-python --zip`** archives into Graph JSON — or straight into a running server. SIDs/GUIDs kept verbatim; unmappable rights reported, never fabricated. |
| **Graph backend** | Stores nodes/edges in **Neo4j** using the **BloodHound CE schema**, so existing BloodHound Cypher queries work. An in-memory store is used for tests and demos. |
| **Ingestion API + UI** (`omenhound serve`) | Go HTTP service that ingests graphs and serves a dependency-free web UI with a force-directed graph view. Ingest can be **merge** (default) or **replace**, can be **scoped to one domain** (rejecting foreign domains rather than mixing them), and is tracked as **batches**. The UI previews an import, lists batch/domain history, and offers **scoped deletion** by batch or domain with a preview-and-confirm workflow, plus a global delete so you can work with one dataset at a time. |
| **Dynamic abuse engine** | For every edge, renders a copy-pasteable abuse command by interpolating **real node properties**, with a per-technique **OPSEC/detection note** and Windows event IDs. |
| **Attack-path analytics** | Fourteen canned, documented queries (Kerberoastable, AS-REP roastable, DCSync, LAPS, delegation, AdminTo, high-value, adminCount, owned…) answered over the current graph at `/api/v1/analytics`, with an **Attack Paths** view in the UI. Each result lists the exact property/relationship that matched, and a zero result says so when the underlying attribute was never collected. |
| **Gated credential ops** | Optional, off-by-default ability to change an AD password over LDAPS (`unicodePwd`), behind token + explicit-approval + audit gates. |

Unlike a static cheat-sheet, the abuse commands are generated at render time.
Select the `jdoe —GenericAll→ WS01` edge and OmenHound prints:

```bash
bloodyAD --host DC.omenhound.lab -d omenhound.lab -u jdoe -p '<password>' set password WS01$ 'NewPassw0rd!42'
# OPSEC: unicodePwd over LDAPS (4724) / RBCD write (5136) ...
```

— with the real sAMAccountName, DN, and domain from *your* graph.

## Quickstart (no domain required)

The `sample` collector ships a deterministic fake domain so you can try the
whole pipeline offline:

```bash
git clone git@github.com:krazybeastx1/omenhound.git
cd omenhound
make build                     # -> bin/omenhound

# 1) collect the sample graph
./bin/omenhound collect --collector sample --out graph.json

# 2) serve the API + web UI (in-memory store)
./bin/omenhound serve --collector sample --addr 127.0.0.1:8080
#    open http://127.0.0.1:8080  — click a node, then an edge
```

Or in one shot: `make run-sample`.

### Collect from a real domain

```bash
export OMENHOUND_PASSWORD='...'          # avoid --password on the CLI
./bin/omenhound collect \
  --collector ldap \
  --domain corp.local --server dc01.corp.local \
  --ldaps --username 'CORP\svc_omenhound' \
  --password-stdin --out corp.json

# push into a running server (requires --api-token on serve)
curl -sS -X POST http://127.0.0.1:8080/api/v1/ingest \
  -H "Authorization: Bearer $OMENHOUND_API_TOKEN" \
  --data-binary @corp.json
```

By default an ingest **merges** into whatever the server already holds. An ingest can be
**scoped to one domain** (`?domain=corp.local`) so a multi-domain file cannot silently
mix domains: objects that declare a *different* domain are rejected (or skipped, with
`on_mismatch=skip`), and objects with no domain are only assigned to the selected domain
when you explicitly ask (`unknown=stamp`). To end up with **only** this collection, use
replace mode — with a domain it replaces just that domain. The web UI's **Ingestion** page
exposes the same scope box, a dry-run **Preview**, a *Replace existing graph* checkbox and
a *Delete data* control, all with the same confirmation steps.

```bash
# merge, but only the corp.local objects (reject anything else)
curl -sS -X POST "http://127.0.0.1:8080/api/v1/ingest?domain=corp.local&on_mismatch=reject" \
  -H "Authorization: Bearer $OMENHOUND_API_TOKEN" \
  --data-binary @corp.json

# replace: delete everything, then ingest this graph
curl -sS -X POST "http://127.0.0.1:8080/api/v1/ingest?mode=replace" \
  -H "Authorization: Bearer $OMENHOUND_API_TOKEN" \
  --data-binary @corp.json

# delete all data (confirmation is required)
curl -sS -X DELETE "http://127.0.0.1:8080/api/v1/graph?confirm=true" \
  -H "Authorization: Bearer $OMENHOUND_API_TOKEN"
```

Imports are tracked as **ingestion batches** (id, source file, selected domain, timestamp,
status, created/updated/skipped counts). The web UI's **Ingestion Management** tab lists
that history, and offers **scoped deletion** by batch or by domain: it previews exactly
which nodes and relationships would be removed and which are **preserved** because another
import shares them, then deletes only after you confirm (a domain deletion requires typing
the domain name). The server re-validates the preview when you confirm, so a stale plan
can never delete more than you reviewed. Scoped deletion needs a store that tracks
provenance — the default in-memory store does; a backend without it returns a clear error
rather than deleting blindly.

### Graph Explorer (web UI)

The Graph Explorer is a dependency-free canvas force layout served from the same
binary — no CDN, no bundler, no third-party graph library. The toolbar is grouped
by purpose:

| Group | Controls |
|---|---|
| Navigation | zoom out/in, fit to view, reset view, center selection, re-run layout, show/hide Inspector |
| Start & selection | **Start from…** picker, start/target chips, set start/target from the selection, clear path highlight |
| Search | find node (name / SAM / SID) |
| Filtering | node-kind filter, relationship filter, **Sessions only**, isolate, hide unrelated edges, clear selection |
| Display | node labels, edge labels, directional arrows, legend |
| Analysis | **Find Paths** between the start and target, open **Path Explorer** from the starting node, toggle the route panel |

Three entity roles are kept deliberately separate and are never inferred from
one another:

* **Selected node** — the entity currently open in the Inspector.
* **Starting node** — the origin of an analysis (set from the picker, the
  Inspector’s *▶ Start here*, or a relationship row). Persists while you inspect
  other entities.
* **Target node** — the destination used by path analysis.

**Starting node.** Type in *Start from…* to search every object; picking a result
sets the starting node, selects and centres it, and shows a `start` chip. The
canvas marks it with a solid **green** double ring and a `START` caption; the
target gets a dashed **red** ring and a `TARGET` caption. Shape, letter and
caption are all present, so the meaning survives greyscale.

**Sessions.** Where the dataset contains `HasSession` edges
(`(User)-[:HasSession]->(Computer)`), the Inspector’s *Sessions* section lists the
observed relationships in both directions, and the *Sessions only* toggle filters
the graph to just those identities and hosts. OmenHound validates no session
metadata, and its collectors emit sessions **without timestamps or validity** —
so the UI states only “observed at collection time” and never asserts an
observed/historical/stale/expired status it cannot prove.

**Credentials.** OmenHound does not store secrets in the graph. The Inspector’s
*Credentials* section therefore usually shows an honest empty state. If an
importer supplies credential **references** through the documented property
namespace below, they are rendered masked by default with an explicit per-value
reveal; raw values never reach the URL, browser storage or logs. A reference is
never treated as proof that authentication would succeed.

```
cred.type        password | nthash | ntlm | kerberos-ticket | token | certificate
cred.source      where the reference came from (collector / import)
cred.ref         an opaque fingerprint or reference id — never the raw secret
cred.observed_at RFC3339 collection timestamp
cred.status      discovered | imported | validated | expired | unknown
```

**Path Explorer.** Source and target can be set from the graph — **Find Paths**
runs the search between the start and target, the *⇄ Paths* button opens the
view from the starting node or the selection — and the **Path Explorer** panel
appears beside the canvas (a collapsed/hidden drawer takes no space from the
graph). Results honour direction (outgoing / incoming / undirected), node and
relationship-type filters, max depth and max paths.

The backend runs a breadth-first search that returns up to *max paths* **distinct
shortest routes of equal length**, not every possible route; when the max-paths
or expansion limit is hit the UI says so instead of implying a complete set. With
no route selected every discovered route is highlighted in its own colour;
selecting a route focuses it, emphasises its nodes with a coloured ring
(intermediate nodes keep their category fill) and dims the other routes without
deleting anything. Unrelated nodes and edges are faded, never removed.

The panel lists, per route: *Path N*, start/target name and type, hop and node
counts, the intermediate nodes in traversal order, the relationship types, and a
status — **complete** (every relationship has an abuse template) or **audit
unknown** (a relationship has no template) — which describes data coverage, never
exploitability. Controls are **Show all**, **Focus**, **↑ Prev** / **↓ Next**,
**⛶ Fit**, **⇄ Reverse** (swap start and target and re-search), **⭳ Export**
(download the selected route as JSON) and **Clear**. Paths are graph evidence: a
connection is never presented as an exploitable attack path.

Keyboard (ignored while typing): `f` fit, `r` reset, `c` centre selection,
`/` focus the node search, `Esc` clear the selection and any highlighted path.

**Data requirements & limitations.** Sessions require a collector that observed
them (`-c session` / `loggedon` over SMB) or an imported dataset that contains
`HasSession`. Credential evidence requires an importer that emits the `cred.*`
namespace; the shipped collectors do not. There is no session/credential schema in
the graph store beyond optional node properties, and the read API does not persist
collection-run metadata, so per-entity provenance is limited to the entity’s own
stable identifiers (SID, or objectGUID when no SID exists).

### BloodHound.py-compatible flags

`omenhound collect` accepts the same short flags as `bloodhound-ce-python`:

```bash
# your existing workflow
bloodhound-ce-python -d cascade.local -u s.smith -p '...' -ns 10.129.46.41 -c all --zip
# ...or drive OmenHound directly, CE-archive output included
./bin/omenhound collect --collector ldap -d cascade.local -ns 10.129.46.41 \
  -u 'CASCADE\s.smith' --password-stdin --use-ldaps -c group,objectprops \
  --zip -op cascade_ --out cascade_bloodhound.zip

# and merge existing BloodHound output into OmenHound
./bin/omenhound import --in cascade_bloodhound.zip --out cascade.json
./bin/omenhound import --in cascade_bloodhound.zip --api http://127.0.0.1:8080 --token "$OMENHOUND_API_TOKEN"
```

`-d/--domain`, `-u/--username`, `-p/--password`, `-ns/--nameserver` (DC SRV
discovery), `-dc/--domain-controller`, `-c/--collectionmethod`, `-op/--outputprefix`,
`--use-ldaps`, `--zip`, `--auth-method`/`--hashes`/`-k`/`--use-kcache`/`--aes-key`/
`--dc-ip`. Every BloodHound.py collection method is implemented (`group`,
`localadmin`, `session`, `trusts`, `objectprops`, `acl`, `container`, `dcom`, `rdp`,
`psremote`, `loggedon`); the SMB/RPC methods run one computer at a time, so raise
`--timeout` for a large domain. An unknown auth method **fails loudly** — it never
degrades silently.

Authentication is **simple bind** by default. `--auth-method ntlm` uses an NTLMSSP
bind (no extra dependency), and `--hashes NT` or `--hashes LM:NT` performs
**pass-the-hash** — the LM half is dropped, since NTLMSSP computes the response from
the NT hash alone. `--hashes` implies NTLM, and cleartext NTLM is refused unless you
pass `--allow-plaintext-ldap`. The SMB/RPC methods (`session`, `localadmin`, `rdp`,
`dcom`, `psremote`, `loggedon`) authenticate over SMB with the same credentials,
including pass-the-hash.

`-k/--auth-method kerberos` performs a Kerberos GSSAPI SASL bind on LDAP and a
Kerberos SMB session, from one credential source:

| Flag | Credential |
|---|---|
| `-p/--password` | password (AS-REQ) |
| `--hashes NT` | NT hash → RC4-HMAC (overpass-the-hash) |
| `--aes-key HEX` | AES-128/256 key |
| `--use-kcache` | the TGT named by `$KRB5CCNAME` |

Kerberos needs the DC **hostname** (`--server dc01.corp.local`), not its address —
a service ticket is issued for a name. Add `--dc-ip` when that name does not resolve
to the KDC. The SMB pass logs on once and reuses the ticket for every host (one
AS-REQ for the run, one TGS per host). The live handshake needs a real domain
controller and is **unvalidated** (no AD lab was available); the flag handling, SPN
construction, credential selection and TGT reuse are unit-tested.

## Security posture

OmenHound handles live credentials and can act on AD, so it treats itself as a
high-value target:

- **Memory-only credentials.** Secrets are held as `[]byte`, never written to
  disk, and explicitly zeroed after use (`internal/creds`). The caller's buffer
  is copied, never aliased.
- **Never logged.** The audit logger redacts any field matching
  `password/secret/token/hash/...` before writing (`internal/audit`).
- **TLS everywhere.** No plaintext LDAP for collection when `--ldaps` is set;
  AD **writes refuse to run without LDAPS** (`internal/act`).
- **Writes are opt-in and gated.** The ingest and credential endpoints require a
  bearer token; the password-change endpoint additionally requires
  `--enable-credential-ops` **and** a per-action `X-Omenhound-Approval: yes`
  header. Every action is audited with actor, target, result, and reason.
- **Bounded input.** Ingestion validates vocabulary, referential integrity, and
  size before touching the store.
- **Honest output.** Missing node properties produce explicit warnings rather
  than silently broken commands.

See [docs/THREAT-MODEL.md](docs/THREAT-MODEL.md) for the full STRIDE analysis,
assets, and residual risks.

## Architecture

```
 collector ──Graph JSON──▶ ingest ──▶ Store ──▶ Neo4j (BloodHound CE schema)
 (ldap/sample)                         │
                                       └──▶ api ──▶ web UI (canvas graph)
                                                └──▶ abuse engine (edge → dynamic command + OPSEC)
```

| Package | Responsibility |
|---|---|
| `pkg/model` | Node/edge vocabulary, `Graph`/`Meta`, SID-keyed identity. |
| `internal/collector` | `Collector` interface; `sample`, `ldap`, SMB probe; SID/DN helpers. |
| `internal/graph` | `Store` interface; `memory` and `neo4j` backends. |
| `internal/ingest` | Validate + write graphs. |
| `internal/api` | HTTP endpoints, auth, static UI, gated writes. |
| `internal/abuse` | Edge → dynamic command + OPSEC templates. |
| `internal/creds` | Session-scoped, memory-only credential store. |
| `internal/audit` | Redacting JSON-lines audit log. |
| `internal/act` | The only package that writes to AD (`unicodePwd` over LDAPS). |
| `web` | Embedded static UI (no build step, no CDN). |

## Development

```bash
make vet test build     # what CI runs
go test ./...           # unit tests
gofmt -s -w .           # format
```

All tests are dependency-free: the graph, abuse, analytics, creds, audit, ingest,
and API layers are exercised against the in-memory store, so nothing requires a
domain or a database.

## Roadmap

- [x] LDAP users/groups/computers + membership
- [x] BloodHound CE-compatible Neo4j schema
- [x] Dynamic abuse commands + OPSEC
- [x] Gated `unicodePwd` password change + audit
- [x] BloodHound CE JSON / BloodHound.py `--zip` **import** and CE-archive **export**
- [x] BloodHound.py-compatible collection flags, method planning, SRV DC discovery
- [x] Token-gated write API in the web UI
- [x] ACL (`nTSecurityDescriptor`) → `Owns`/`GenericAll`/`WriteDacl`/`GetChanges`/… edges
      *(parser and ACE mapping unit-tested against impacket-generated descriptors; the live LDAP path is code-only — no AD lab)*
- [x] OU / GPO / container → `Contains` + `GPLink`, and domain trusts → `TrustedBy`
- [x] SMB sessions & local groups (`HasSession`, `AdminTo`, `CanRDP`, `ExecuteDCOM`,
      `CanPSRemote`) — `-c session,localadmin,rdp,dcom,psremote,loggedon`
      *(filtering/resolution unit-tested; DC local groups are skipped; the live SMB/RPC path is code-only — no SMB host was available)*
- [x] NTLM bind (`--auth-method ntlm`) and pass-the-hash (`--hashes`) over LDAP/LDAPS and SMB
- [x] Kerberos (`-k`/`--auth-method kerberos`) over LDAP GSSAPI SASL and SMB, from a
      password, NT hash (`--hashes`), AES key (`--aes-key`) or ccache (`--use-kcache`)
      *(flag handling, SPN construction and credential selection are unit-tested; the
      live handshake is code-only — no domain controller was available)*
- [x] Canned attack-path analytics (Kerberoastable, AS-REP roastable, DCSync, LAPS,
      delegation, AdminTo, high-value, adminCount, owned…) exposed at
      `GET /api/v1/analytics` and shown in the **Attack Paths** UI view
      *(unit-tested; queries key off BloodHound CE property/edge names and flag when
      the data they need was never collected)*
- [x] Start→Target path highlighting in the Graph Explorer: multi-route shortest-path
      search, a collapsible **Path Explorer** panel, per-route colouring, green START /
      red TARGET markers, reverse search and JSON export
      *(pathfinder and highlight state unit-tested; the UI is driven end-to-end in a real
      browser — the Neo4j path backend is code-only, no live database in CI)*
- [x] Domain-scoped ingestion and ingestion management: imports can be constrained to one
      domain (foreign-domain objects refused, never mixed), are tracked as **batches**, and
      can be **deleted by batch or domain** with a preview-and-confirm workflow that
      preserves records other imports share
      *(provenance, scoping and deletion unit-tested; the UI is driven end-to-end in a real
      browser — scoped deletion needs a provenance-tracking store, so it is unavailable on
      the Neo4j backend, which returns a clear error instead of deleting blindly)*
- [ ] Provenance-aware scoped deletion on the Neo4j backend (batch/domain tags + migration)
- [ ] Incremental collection with SID-keyed merge and stale-edge expiry
- [ ] Customized BloodHound CE frontend (BloodHound CE is written in Go; stock CE UI as fallback)
